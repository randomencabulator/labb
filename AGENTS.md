# AGENTS.md

This file provides guidance to agents when working with code in this repository.

## What this is

A LangGraph chat agent with two front ends that share one graph, one history database and one context-compaction step:
- **`labb`**: a coding agent for the terminal (`cli/app.py`, entry point `labb.cli.app:main`), run in any directory.
- **Web chat**: a FastAPI server (`server/app.py`) serving a React/Vite app from `frontend/web/dist`. It also acts as an auth gateway to Ollama and labb-web-search-crawler for labb installs on other PCs, and receives their synced sessions.

Next to them, and not part of the labb package:
- **labb-sites** (`sites/`): static website hosting, a service of its own. See **labb-sites** below.
- **Design system** (`frontend/design-system/`): labb's look as tokens, React components and a docs site, plus an Agent Skill that teaches coding agents to build web UI with it. See **Design system** below.
- **iOS app** (`mobile/ios/`): a SwiftUI client of the server, with the web chat's features in iOS patterns. It asks for the server's address, then signs in like the web app (session cookie, `X-Labb: 1`). It takes its look from the design system's Swift package (`frontend/design-system/swift`, a local package). `mobile/README.md` explains its layout (`Core/` is the API client, models and a port of `useChat`/`turnsReducer`; `Features/` holds the screens) and the `LabbUITests` walkthrough. A change to an endpoint or event the web app uses should reach the app too.

`README.md` is the project's front page (what labb is, Docker and install quick starts, the main settings); keep it short and inviting. `docs/guide.md` is the full user reference (commands, settings, server, documents, memories, API), and `docs/images/` has the README's screenshots. Keep them up to date when behavior changes.

## Commands

```bash
uv sync --all-groups                            # first, in a fresh checkout
uv run pytest                                   # all tests (no model or Ollama needed)
uv run ruff check . crawler sandbox spawner browser sites   # mistakes only (pyflakes), as CI does
uv run pytest tests/test_permissions.py         # one file
uv run pytest tests/test_graph.py -k <name>     # one test
TEST_DATABASE_URL=postgresql://… uv run pytest  # the same tests on Postgres (empties that database first)
uv run labb                                  # run the terminal agent from the checkout
uv run labb --graph                          # print the graph as Mermaid
uv run python -m labb.server.app              # web server on :8000 (PORT to change)

cd frontend && npm install                      # the web app and the design system: one npm workspace in frontend/
cd frontend && npm run web:build                # build the web app (server serves frontend/web/dist)
cd frontend && npm run web:dev                  # Vite on :5173, proxies API to :8000 (or npm run dev in frontend/web)
cd frontend && npm run web:typecheck

docker compose up -d --build                    # server image: web app + server + labb wheel (needs ./setup.sh dev once: COMPOSE_FILE with compose.dev.yaml in .env)

open mobile/ios/Labb.xcodeproj                  # the iOS app (SwiftUI, Xcode 26, with the design system's Swift package; see mobile/README.md)
cd frontend && npm run docs:dev                 # design system docs (Next.js) on :3200; see frontend/design-system/README.md
cd frontend && npm run typecheck                # the design system (stale tokens or skill fail it) and the web app
cd frontend && npm run docs:build               # tokens, the skill, then the docs as static HTML in frontend/design-system/docs/out
```

Requires Python 3.14 and uv; Node 22+ for the web app (the design system's scripts run TypeScript with Node itself: Node 24 is safest). Ruff checks for mistakes only (`[tool.ruff]`: `E9`, `F`); there is no formatter, keep the hand style. CI (`.github/workflows/ci.yml`) runs all of it, the services' tests, Postgres, and the frontend. `docs/improvement-plan/` tracks the audit's open items.

**npm workspace:** `frontend/` holds the JavaScript side, kept apart from the Python project. `frontend/package.json` makes `web`, `design-system/packages/*` and `design-system/docs` (paths inside `frontend/`) one npm workspace with one lockfile (`frontend/package-lock.json`) and one `frontend/node_modules`, so there's a single React. Install in `frontend/` (`npm install` in `frontend/web/` does the same); run npm commands there, and add a dependency to one part with `npm install <pkg> -w web` (or `-w @labb/ui`, `-w @labb/design-docs`). `frontend/web/` depends on `@labb/tokens` and `@labb/ui` by version (`^0.1.0`), and npm provides them from `frontend/design-system/packages/` (no publishing, no `file:` links), so a change there is in `frontend/web/` at once. The Dockerfile installs with `npm ci -w web`, which brings the web app, the design system packages it uses and their dependencies, not the docs site.

## Architecture

**Layout:** the package is `src/labb/` and imports are absolute (`from labb import llm`). Paths below are relative to it.
- top level: the shared core: the graph (`agent.py`, `state.py`, `model.py`, `tool_node.py`, `end_logic.py`, `continuation.py`), `engine.py`, `llm.py`, `context.py`, `runner.py`, storage (`db.py`, `chats.py`, `usage.py`, `memories.py`), `settings.py`, `permissions.py`, `hooks.py`, `export.py`, `remote.py`
- `tools/`: the toolsets
- `cli/`: terminal-only: `app.py` (arguments, the chat loop and slash commands), `render.py` (the streaming reply view and the shared `console`), `account.py` (`--login`, `--logout`, `--update`), `connect.py` and `channel.py` (`labb connect`), `input.py` (the prompt), `mcp_servers.py`, `snapshots.py`, `sync.py`
- `server/`: server-only: `app.py` (FastAPI), `auth.py`, `auth_routes.py`, `browser_routes.py`, `browser_sites.py`, `usage_routes.py`, `documents.py`, `documents_routes.py`, `memories_routes.py`, `memory_index.py`, `gateway.py`, `install.py`, `pcs.py`, `pcs_routes.py`, `pc_team.py`, and `studio/` (workflows)

`cli/` and `server/` import the core, never each other, and the core imports neither.

**Graph** (`agent.py`): `START → recall → compact → llm_call → (tool_node → compact …) | (compact …, going on) | END`. `agent.py` loads `.env` *before* importing other modules because `llm.py` reads env and creates the model at import time. `chat_agent` is the compiled graph with the checkpointer from `db.checkpointer` (`SqliteSaver`, or `PostgresSaver` on a pool with `LABB_DATABASE_URL`).

**Data dir:** if `pyproject.toml` sits above `src/labb` (checkout or editable install), `.env` and `chats.sqlite` live in the project dir; an installed wheel uses `~/.labb/`. `CHAT_DB` overrides the database path.

**One run path for both front ends:** `runner.run_reply()` streams one message through `chat_agent`, emitting JSON-able events (`token`, `thinking`, `tool_call`, `tool_result`, `compact`, `continue`, `retry`, `error`, `done`/`stopped`). It handles stopping (a `threading.Event` checked by a callback handler, which also reaches tools like `run_command`), saving partial replies, per-thread locks, replacing turns (edit/regenerate, `/undo`), stats and titles. `cli/app.py` and `server/app.py` are mostly UIs around it.

**Going on** (`continuation.py`, called at the end of `model.llm_call`): a reply without tool calls ends the turn only when it ended as it should. `end_reason` reads the provider's stop field (`done_reason`/`stop_reason`/`finish_reason`/`incomplete_details`) and the reply: `truncated` (cut off; a cut-off tool call is dropped with `without_tool_calls`), `empty` (dropped from the messages, its cost through `count_usage`) or `done`. A `done` then passes `gates`, in order, each worked out only if the ones before don't apply (a Stop hook runs a command), and the first under its cap wins: `open_steps` (todo steps `pending`/`in_progress`, unless the reply ends with `?`, the run is in plan mode, or this reply called no tool: it only answered something in between; the note lists the steps), `announced` (a short reply ending in what the model will do: with open steps up to 600 chars, without a list up to 300 and only after a tool call this reply, so a greeting isn't one), `loop_unscheduled` (a self-paced loop run without `schedule_next`/`end_loop`), `goal` (an active goal, `tools/goal.py`; in the terminal not after a `?`; `goal.next_round` counts it), `hook` (a `Stop` hook exited 2, `hooks.has`/`around` with `extra`), and `audit` (off by default: `update_todos` was called this reply or a goal is active). `goals.count_call` counts every model call against an active goal; the call that spends its budget sets `budget_limited` and gets `continue_goal_budget`, as `goal_budget` if the reply was `done`, else as a plain note for the next call. For those, up to `Engine.continues(reason, task)` per reply (`engine.CONTINUE`, `TASK_CONTINUE` for a task's run unless the overlay says, the overlay's `continue`), `review` sets the state's `continuing` and `continued` and leaves the engine's `continue_*` prompt in `notes` (model input only, after the reply), and `end_logic.should_continue` goes to `compact` (an engine's loop: wherever `tool_node` leads, in `engine_steps.compile_loop`). `runner.run_reply` empties both at the start of a reply, `save_stopped_reply` clears `continuing` so a stopped thread has nothing pending, and `ReplyStats` keeps `end_reason` and `continued`. The reason is also in the reply's `response_metadata["end_reason"]`, never sent to a provider.

**Model calls that fail** (`model.call_model`): `llm.is_transient` (busy, rate-limited, 5xx, a broken or quiet connection; never credits, keys or a missing model) is tried again after `RETRY_WAITS` (or Retry-After, up to `MAX_RETRY_WAIT`), on the stop flag so a stop ends the wait; each try writes `{"retry": …}` to the graph's `custom` stream, which `run_reply` turns into a `retry` event and the UIs use to drop what the failed call wrote. Ollama's client gets a read timeout of `llm.STALL_SECONDS` (`MODEL_STALL_SECONDS`): without one a stalled stream never ends, and `StopOnRequest` only acts on a token.

**Per-run behavior lives in `config["configurable"]`**, not globals:
- `workdir`: set only by the terminal. Its presence (`has_workdir`) decides which tools are offered: toolsets with `NEEDS_WORKDIR = True` (files, shell) and the settings' MCP tools are terminal-only; the server's MCP tools (`server/mcp.py`, `tools.server_tools`, the pseudo-toolset `mcp`) are offered only without one, to the default assistant. `server/mcp_registry.py` finds servers to add (`GET /admin/mcp/catalog`: its `FEATURED` list, then a search of the MCP Registry, cached): each as options, a config with `{{FIELD}}` placeholders plus the fields to ask for, which the page fills in (`fill` in `McpServers.tsx`) and saves through `PUT /admin/mcp` like any other.
- `tools`: a `tools.ToolRules` (terminal only: `--tools`, `--disallowed-tools`, the settings' `tools`, `/tools`), which `tools_for`/`prompts_for`, `model_with_tools` (cached per rules) and `tool_node` (refuses the rest) apply on top of the agent's toolsets.
- `loop`: a `tools.loop.Loop` on the terminal's `/loop` runs only (`cli/app.py`'s `loop_command`, `after_loop_run`; `cli/input.prompt_until` gives up the prompt with `LOOP_DUE` when a run is due). The `loop` toolset (`schedule_next`, `end_loop`) is `ONLY_IF_ALLOWED`, and `tools.offered_for` adds it for those runs; `model.system_prompt_parts` adds `Loop.prompt_section()`. `after_loop_run` tries a failed run again after `FAILURE_WAITS` (`Loop.failures`), and runs a self-paced one that didn't schedule again after its `last_wait` once (`Loop.unscheduled`, `MAX_UNSCHEDULED`).
- `answer_mode` (`fast`, `auto` or `thinking`, from `llm.ANSWER_MODES`: `llm.mode_options` turns it into the call's arguments per provider in `model.call_model`, and `model.MODE_PROMPTS` adds a system prompt line; set by `/chat`'s `answer_mode` and the terminal's `/answer`, `--answer`, `answerMode`). Reasoning reaches the UIs through `runner.thinking_of` (Ollama's `reasoning_content`, Anthropic's thinking blocks). OpenAI's own API (`llm.is_openai_api`) is called through Responses (`use_responses_api`): newer models refuse tools with a `reasoning_effort` through Chat Completions, which OpenAI-compatible servers keep. Ollama models are `llm.OllamaChat`, which hands its adapter only blocks it takes (`llm.for_ollama`): another provider's thinking from before the model was changed is left out, and files or tools' resources become a note, instead of failing the call.
- `model`, `mode` (plan mode), `allow_all`, `approve` (the CLI's approval callback), `ask_user` (the CLI's callback for the `ask_user` tool's questions), `hooks`, `git_context`, `thread_id`, `stop_requested`.
- `model.workdir(config)` and `llm.for_config(config)` are the accessors.

**Engines** (`engine.py`, runtime in `engine_steps.py` and `tools/custom.py`, terminal in `cli/app.py`'s `engine_command` and `pick_engine`, server in `server/engines.py` and `engines_routes.py`, UI in `frontend/web/src/components/engine/`, `EnginePicker.tsx`): the agent's core as an overlay on the defaults, which live in `engine.py` (the prompts and context numbers; `model`, `context` and `runner` re-export the old constant names). The default is the empty overlay and goes through the same code, and `tests/test_engine_golden.py` holds it to a recording (`tests/golden/engine_default.json`; `UPDATE_GOLDEN=1` rewrites it, only for a change to the default that's meant). `engine.of(config)` is `configurable["engine"]`, else the run's agent's (`agents.for_run` puts it there, so tasks and workflow steps get it), else `DEFAULT`. New settings go in `check` (unknown ones are refused, not ignored), what the editor offers comes from `engines_routes.catalog` (a test holds it to the settings), and values are read through the `Engine`, never a constant.
- **Only narrowing:** `tools.rules_for` merges an engine's `allow` (as `ToolRules.within`) and `deny`, so `tool_node`, `model.tools_of` and the `task` helper all apply it; anything that reads `configurable["tools"]` directly would bypass it. Custom tools are `custom__<name>` (toolset `custom`, in `offered_for`'s "everything", so agents don't get them), and a command tool calls `run_command`, so approvals and plan mode apply.
- **Loops:** `check_loop` is what makes a loop safe to run (every way out goes to one place, so one step at a time; tool calls always reach `tool_node`; a way to the end; no round without the model). `engine_steps.graph_for` compiles it (cached); `llm_call`, `tool_node`, `compact` and `recall` keep their names because `runner` and `update_state` use them. The state's channels (`vars`, `notes`, `visits`, `route`, `step`) are the same for every engine, which is what lets a chat move between them (`tests/test_engine_threads.py`); `get_state` on `chat_agent` reads any thread. `model_call_cap` (`limits_for`) is checked before each model call, since the recursion limit assumes 3 steps per call. Side calls (`model_step`, prompt tools) report through `configurable["count_usage"]` (`ReplyStats.add_side_call`) and go through the run's callbacks, so budgets see them. A step's `step` update becomes tool call and result events (`runner.step_events`), named `step: <label>`.
- **`tool_shape()`** is the extra key of `model_with_tools`' cache, None unless descriptions, strict mode or custom tools change, and then the fifth argument is left out. `{{today}}` and `{{workdir}}` are filled in only in the engine's own texts, never in what projects or users wrote (`theirs` in `system_prompt_parts`). `instruction_files` are plain names only, since they're read into the prompt.
- **Running code:** hooks and `check` need a working directory; `terminal_only`/`web_problems` keep such engines off the web, and `/chat` refuses them. Python goes through `custom.run_python`: `custom.sandbox` (set by `server/app.py`, always, so the server never runs it itself), else a subprocess in the terminal. `needs_trust` says what asks first, per content hash in `~/.labb/trusted-engines.json`.
- **Server:** the read-only ones that come with labb are `engines.BUILT_INS`: `default` (the empty overlay, what falls back) and `labb-local` (`engine.LOCAL_OVERLAY`, resolved once as `engine.LOCAL_ENGINE`; the terminal lists it from `engine.entries`, and no file or fork can take its name): fewer tools, short prompts and descriptions, for small local models (plan and measurements in `local-engine-docs/`). A pick of the removed `labb-web` (a chat's, a default, an agent's) isn't `visible`, so it falls back like any engine that's gone. Every overlay save is an immutable `engine_versions` row. A chat's pick is `chats.engine_id`; `engines.for_run` is the order (picked, chat's, agent's, yours, server's). Trying a draft and comparing use `try-` threads like agents' Try it (`engine_draft`, `trial` on `/chat`). The preview runs `inspect_context` with `configurable["preview"]`, a made-up workdir for terminal runs, and that flag keeps it from reading the server's own files.

**Tool calls** (`tool_calls.py`): `llm_call` gets the raw reply from `model.call_model` (strict tools where `llm.Models.strict`, from `llm.uses_strict`/`STRICT_TOOLS`/the provider's `strict_tools`; a strict refusal adds the spec to `model.strict_refused` and retries once), then `tool_calls.fix` repairs names and arguments, takes back `invalid_tool_calls`, and for Ollama asks `model.constrainer` (the `constrained_model` with `format`, no callbacks so nothing streams). What it did is in `response_metadata["tool_fixes"]`, counted by `ReplyStats` into `tool_repaired`/`tool_constrained`/`tool_failed` (usage columns, added to older databases with `db.add_column`) and shown in the terminal as `fixed`. `labb eval tools` (`cli/evals.py`, prompts in `cli/tool_eval_cases.py`) scores models the same way.

**Parallel tool calls** (`tool_node.py`, `tools.run_together`, `tools.parallel_limit`): neighbouring calls whose tools are in a toolset's `RUN_TOGETHER` run at once on daemon threads (not a pool's, whose workers hold up the exit), each with a copy of the context, at most `parallel_limit()`, which `server/app.py` sets to the limit `tool_parallel` and `apply_settings` to `parallelTools`. Any other call is a barrier and runs alone on the node's thread. **Only tools that just read go in `RUN_TOGETHER`**: on a stop the batch gives up on what's running and answers `CANCELLED`, so a call can be abandoned halfway. Anything sharing state needs a lock first, and a model call inside needs `ReplyStats` and `Budget` made thread-safe, which is why `task` and `ask_agent` aren't in (`task`'s helper reports through `count_usage` and the run's `Budget`, neither thread-safe; `ask_agent`'s spending isn't metered). PreToolUse hooks run in order before the batch and PostToolUse ones as each call finishes, always one at a time on the node's thread. Results go back in the calls' order and are written to the graph's `custom` stream as each is ready (`writer`, a node parameter), which `runner.run_reply` handles before looking for a stop, since leaving mid-step would lose the step's results; the `tool_node` update only reports what wasn't. A question from a call given up on is answered no in `cli/app.ask`.

**Tools** (`tools/__init__.py`): each module in `TOOLSETS` exposes `TOOLS`, an optional `PROMPT` (appended to the system prompt) and optional `NEEDS_WORKDIR`. MCP tools are injected at runtime via `set_extra_tools` (the terminal's) and `set_server_tools` (the server's); the client is `mcp_client.py`, which takes a `permission` function. In the web chat, a tool that needs approval emits an `approval` event from `server/app.chat_approver` and waits for `POST /chat/approve`. `model_with_tools` is `functools.cache`d per `(spec, has_workdir)`. Tool errors go back to the model as the tool result instead of raising (`tool_node.py`).

**System prompt** (`model.system_prompt`): in the terminal, who labb is and `CODING_PROMPT` (how it works on a request: understand, ask only when it matters, plan, change, check, report; keep it short, small models read it), toolset prompts, git context captured once per session (kept stable for prompt caching), and `AGENTS.md`/`CLAUDE.md` files from the workdir up to `$HOME`, closest last.

**Context** (`context.py`): large results before the state's `cleared_before` are cleared (`clear_before`; unread ones never are). The `compact` node moves it with `clearing_boundary`, in jumps and only forward: once the read results still in full pass `clear_at` of the window, to the `keep_tool_results`-th (3) from the last, so between jumps the input only grows at its end and providers' prompt caches hold. A state without `cleared_before` (a chat from before it, an engine loop without `compact`) and an engine keeping 0 use the old count (`clear_old_tool_results`, also the `task` helper's). `runner.take_back` moves it back to the removed turn. When 2 or more unread results don't fit, `model.model_input` calls `fit_unread_results`: up to `compact_at`, short ones stay whole and the rest get a fair share, at least `MIN_SHARE_CHARS`, cut with a note for `look_back`; then `cap_results` cuts any tool result over `max_result_share` of the window (MCP and custom tools have no cap of their own). `compact` counts unread results whole but capped (`input_tokens`), so older turns are summarized first. `token_scale` compares against the whole results, so after a cut it reads 1.0 for that round; above `compact_at` (75%) of the context window, `compact` first clears as far as it goes (`pressed`), then, once per summary, may hand back the engine's `context_flush` note (`flush`, set by `model.compact_context` when the run has notes or todos, and `flushed` in the state) so the model saves notes before the summary, if there's under 90% used; then older turns are summarized into `summary`/`summarized` in the graph state (`state.py`). `summarize` goes in `chunks` of 60% of the summary model's window, caps results, gives the summary model `facts` (`model.work_facts`: goal, todos, plan path, notes' topics) and appends `recent_files` (from tool calls, not the model) to the summary; Ollama's summary model gets `num_predict` from `summary_share` (`summary_tokens`, 1k–8k) by `model_copy`. `user_words` keeps the user's messages of the summarized part word for word (newest first up to `user_words` of the window, attachments named) in the state, and `with_summary` sends them after the summary. `model.work_reminder` adds the goal, the todo list (`todo.short_show` over 8 items), the approved plan's path and the notes' topics; `model.context_note` adds how full the context is from two thirds of `compact_at`, in steps of 5%. `model.project_instructions` cuts each file at `instruction_limit` (also `max_instruction_share` of the window) with `cut_instructions`' note naming the file and the cut part's headings. **Tool search** (`tools/tool_search.py`): when `tool_share` of the window can't hold the offered tools' schemas, the deferrable ones (MCP tools without `alwaysLoad`, toolsets with `DEFERRABLE`: gmail, calendar) wait: `model.tools_of(config, state)` and `model_with_tools(..., hidden=)` leave them out until a `find_tools` result's "Loaded:" line names them (`tool_search.loaded` reads the messages, so nothing else keeps it), the system prompt's `deferred_tools` section lists them, and `tool_calls.fix` checks calls against `tools_of(everything=True)`. `read_file` answers "Unchanged since #N" (`files.still_seen`) for the same path and text still in full, which `tool_node` makes possible by passing `summarized` and `cleared_before` with `history`. The checkpointed messages stay complete, and `tools/history.py`'s `look_back` reads them by number (a cleared note says `#N`, its index in `state["messages"]`; the summary says which numbers it covers) or searches them; `tool_node` passes them in `configurable["history"]`. It's in `OWN_SWITCHES` and every agent has it. `model.model_input` is exactly what `llm_call` sends; `model.inspect_context` (built on `context.inspect`, with the system prompt's labelled `system_prompt_parts`) breaks it down into tokens per part for the terminal's `/context` and `GET /context`. The web chat's context panel (`frontend/web/src/components/context/`, docked beside the chat at `/chat/<id>/context/<tab>`) uses that, with the message box's model, answer mode, Web and engine as query params, built by `server/app.py`'s `inspection_config` the way `/chat` builds a run so the numbers are the next message's; What-if is the same route with other choices. `GET /context/work` is `inspection.work` (the conversation's todos, goal and approved plan, from `work.py`; for a PC session asked of the PC as `what: "work"`, for a synced one a 400 while it's offline), the panel's Work tab (`WorkTab.tsx`, polling while a reply streams, not waiting for the inspection), `GET /context/raw` is the input as JSON, `GET /context/message` a saved message by index, and `POST /context/summarize` is `compact_context(force=True)` under `runner.lock_for` (409 while a reply or task writes in the chat). The Timeline tab's Tokens view reads `usage_metadata` off saved replies (`context.timeline`): `chats.prune` keeps only the latest checkpoint, so a past call's input can't be shown, and only the latest summary boundary is known. A summary's own call isn't a saved reply, and isn't in the usage ledger either. Its Waterfall view reads `GET /context/traces`: `trace.Trace` is a callback handler `runner.run_reply` passes to the run, recording each model call, tool call and graph step with its start and end. It's saved in the `traces` table by reply, in `trace.live` while the reply is written, and goes with the reply or chat like `stats`. `parent` is what a call ran inside, inferred from the thread for what a tool calls (a tool gets the config it was called with, not one under its own run), so nesting isn't mistaken for parallel. A tool holds its thread until it returns, also in a batch (see **Parallel tool calls**), so `parent` still tells nesting from overlap, and `Waterfall.tsx` tags what overlaps as parallel. The answers themselves are `inspection.py` (`seen`, `raw`, `message`, `traces`, `summarize`), shared by the server and the PC: for a session on a PC (`app.pc_session_of`, looked up before `check_access` since it's in the chat list only once synced), each `/context` route asks the PC (`pcs.ask_context`, through the generic `pcs.ask` that notes use too: a question down the PC's line, answered at `POST /pcs/answers/{id}`, waiting `CONTEXT_SECONDS`). `cli/connect.py`'s `answer_context` hands it to the session's `labb --channel` process (started if it isn't running), whose `Channel.on_context` is `cli/app.answer_context`: the same `run_configurable` its replies use, so the prompt, tools, `AGENTS.md` and settings are the PC's. Its answer is a `context_answer` line on stdout (`channel.write_line`, locked, as reply events share stdout), which `Session._pump` posts back instead of passing to a reply. The page offers the panel for a session only while its PC is online, with the PC's model and Web on.

**Permissions** (`permissions.py`): read-only commands run immediately; others go through the `approve` callback. "Always" saves a command prefix to `<workdir>/.labb/permissions.json`. Settings come from `~/.labb/settings.json` merged with `<project>/.labb/settings.json` (`settings.py`).

**Integrations** (called apps in the code, routes and tables: `connections.py` in the core, `server/connections.py` and `server/connections_routes.py`, tools in `tools/google_calendar.py`, `gmail.py`, `outlook_calendar.py`, `outlook_mail.py`, `github.py` and `notion.py`, UI in `frontend/web/src/components/Integrations.tsx`, whose two Settings tabs are `integrations` and the admins' `integrations-setup`, the old `connected-apps` and `apps` addresses going to them): `server/connections.py`'s `APPS` registry (Google, Microsoft 365, GitHub, Notion: endpoints, scopes, what each allows, its setup `steps`, and how it differs: `pkce`, `token_auth` (Notion's Basic auth and JSON), `any_redirect` (GitHub), `refresh_scopes` (Microsoft), the account from the ID token or `account_url`, `revoke_style`; tokens without `expires_in` or a refresh token never expire, `NEVER`) and its OAuth clients in `app_clients` (admins; `<NAME>_CLIENT_ID`/`_SECRET` under them, `MICROSOFT_TENANT`), people's tokens in `app_connections` (per `(user_id, app)`, both Fernet-encrypted with `studio/secrets.py`'s key, `status` `ok` or `expired`). **Storage** (`chats.py`): besides LangGraph's checkpoint tables, the database has `chats` (web chat list), `cli_sessions` (terminal threads `cli-<id>` per directory) and `stats` tables.

**Database** (`db.py`): SQLite (`CHAT_DB`) by default, Postgres when `LABB_DATABASE_URL` is `postgresql://…` (the server in Docker; labb on PCs never). Every module shares `chats.conn` and `chats.lock`; with Postgres, `conn` is a `PostgresConnection` that takes the same SQLite-style SQL (`?` placeholders, turned into `%s`, literal `%` doubled; client-side binding, so `? IS NULL` works) and makes `with conn:` a transaction. Write queries both understand: `INSERT … ON CONFLICT` (never `INSERT OR REPLACE`/`OR IGNORE`), `IS DISTINCT FROM` (not `IS NOT ?`), qualified columns in `DO UPDATE SET` (`gateway_usage.requests + excluded.requests`), aggregates for every non-grouped column, no `rowid` (`tasks.NEWEST_RUNS`), no NUL characters in text. Use the helpers for the rest: `db.has_table`, `db.local_day`/`local_hour`, `db.json_entries`, `db.group_concat`, `db.size`. psycopg is in the `server` group, imported only for Postgres. Postgres's checkpointer keeps channel values in `checkpoint_blobs`, which `chats._prune_postgres` cleans. Run the tests on both when a change touches SQL.

**Embedding model** (`server/embedding.py`): `index_id()` (the model, plus `+passage-prompt` when passages get a prefix) is what `vectors.model` and `documents`/`memories.embed_model` hold. `save` checks the model with Ollama's `/api/embed`, deletes vectors of other models and runs `on_change` (`app.embed_again`: `documents.reset_store`, `reindex_stale`, and the memory index's `reset` and `reindex_stale`). `_saved` and `_in_use` take `chats.lock`, so they run once at import and `current()` only returns the result: it is called with that lock held.

**Vectors** (`server/vectors.py`): a `vectors` table, one row per `(kind, model, id)` with `user_id`, `doc_id`, `text`, `meta` (JSON) and the unit-length `embedding`. On Postgres with pgvector (`PGVECTOR`, decided by the column's type when the table is made) it's a `vector` with no fixed size (no ANN index: searches are exact over the user's rows, which is plenty here) plus a generated `tsv` (`to_tsvector('simple', text)`, GIN) for keywords; otherwise float32 bytes, searched in Python with `math.sumprod`. `Store.search(..., hybrid=True)` takes the closest by meaning and the best keyword matches (any of the query's words) and fuses their ranks (`fuse`, reciprocal rank fusion); `score` is always the cosine similarity. `Store.replace` embeds first, then swaps the rows in one transaction. Tests use a `Store` with `WordEmbeddings` and model `"test"`.

**Design system** (`frontend/design-system/`, part of the npm workspace in `frontend/`; **read `frontend/design-system/AGENTS.md` before changing anything there**, it has how everything works and how it's meant to be distributed):

UI uses system colours only, never the palette or a literal colour. The other tokens are `--lb-space-*`, `--lb-radius-*`, `--lb-text-*`, `--lb-weight-*`, `--lb-shadow-*`, `--lb-motion-*`, `--lb-border-*`, `--lb-z-*`.
- **Where it stands with the apps:** its values came from `frontend/web/src/styles.css` (each system colour's `web` field names the variable it came from), and `frontend/web/` has `@labb/tokens` and `@labb/ui` as dependencies through the workspace, but doesn't use them yet: work in `frontend/web/` still uses `frontend/web/src/styles.css`'s own variables (`--bg`, `--accent`…). Moving over starts with importing `@labb/tokens/tokens.css` and `@labb/ui/styles.css` once in `frontend/web/src/main.tsx`. A change to the web app's look should also go into the design system's tokens, or the two drift apart until `frontend/web/` moves over. The iOS app does use it: `LabbDesign` (`frontend/design-system/swift`), a Swift package whose `Tokens.swift` and colour asset catalog the token build generates from the same JSON (so a token change reaches iOS on the next `npm run tokens`), with SwiftUI styles and views on top; the app adds it as a local package. Views there use `Color.labb.*` and the `Labb*` tokens, never literal colours.
- **The agent skill, `labb-design-web`** (`frontend/design-system/skills/labb-design-web/`: `SKILL.md`, `references/tokens.md`, `references/components.md`): teaches an agent building web UI to load `@labb/tokens/tokens.css` and `@labb/ui/styles.css` once at the root (with `lb-root` on `<body>`, themes through `data-theme`), use `var(--lb-sys-color-*)` for every colour and the other tokens for as much else as possible, reach for `@labb/ui` first, and check light, dark, a phone width and the keyboard. Use it when building a page, site or component that uses the design system.
  - **It isn't installed in this repo** (nothing scans `frontend/design-system/skills/`), on purpose: `frontend/web/` doesn't load these variables yet, so it would point agents at the wrong ones there. To use it in a project, copy or symlink the folder into that project's `.claude/skills/` or `.labb/skills/` (or `~/.claude/skills/`, `~/.labb/skills/`); agents see its name and description, load it when a task matches, and `/labb-design-web` loads it on purpose. labb's web app takes it as a zip on the Skills page. Install it here once `frontend/web/` uses the design system.
  - **It's generated** from the tokens and the component registry by `frontend/design-system/docs/lib/skill.ts` (`npm run skill`; the rules are written there), so never edit the folder by hand; `npm run typecheck` fails if it's stale. A change to how UI should be built with the system (a rule, a colour people reach for, a component) belongs in `skill.ts` too.

## Conventions and gotchas

- The package and its command are `labb`. The version comes from `remote.version()`.
- **Bump `version` in `pyproject.toml` (and run `uv lock`) whenever a change touches what labb runs** (anything in `src/labb` except `server/`). `labb --update` on the PCs only compares that version string with the server's `/version`; if it's unchanged, they report "up to date" and keep the old code, even after the server's image is rebuilt (`docker compose up -d --build`). Patch bump for fixes, minor for features.
- **Images and releases:** `compose.yaml` pulls labb's images from GHCR (`ghcr.io/randomencabulator/<image>:${LABB_VERSION:-latest}`); `compose.dev.yaml` adds `build:` with local `:dev` names, used when `.env` has `COMPOSE_FILE=compose.yaml:compose.dev.yaml` (`./setup.sh dev`). A new service with its own image goes in both files and in `release.yml`'s matrix. A `v<version>` tag runs `.github/workflows/release.yml`: images to GHCR, `labb-server.tar.gz` (compose.yaml pinned to that version, setup.sh, .env.example, caddy/, backup/) and the wheel on a GitHub release, PyPI when `PUBLISH_PYPI` is set.
- Tests (`tests/conftest.py`) set `CHAT_DB` to a temp file and `CONTEXT_WINDOW=32768` before importing project modules. The `fake_model(ai("text", [(tool, args)]), …)` fixture monkeypatches `model.model_with_tools`; `config` gives a run config with a `workdir`; `client` is a FastAPI `TestClient` authed as an admin.
- The default model is a small local one (`ollama:gemma4:e4b`): keep prompts short and concrete. `edit_file`/`write_file` (`tools/edits.py`) ask with a diff through `approve`, like commands (rule `edits`); turn them off with the tool rules if a model can't make exact edits.
- In a project, `.labb/` holds labb's files: `settings.json`, `permissions.json`, `skills/`, `commands/`, the agent's `notes.md` (`tools/notes.py`, entries under `## topic` headings; see **Notes**) and its todo lists per thread in `todos/` (`tools/todo.py`, git-ignored). In the terminal, `model.model_input` ends with `model.work_reminder` (the open todo list and `notes.topics`) through `with_reminder`: added to the user's last message, or after tool results as a message of its own (added to a result, small models took it for the tool's output); model input only, like recalled memories. App chats get no `context_note`. In the terminal, `/compact` and the `compact` node summarize with `context.CODING_SUMMARY_PROMPT` (`model.summary_prompt`).
- Docstrings and comments are short and in plain prose; follow the existing style.
- **Fetching an address a model or a person gave goes through `safe_http`** (`pin` per hop, or `get`): it checks the name's addresses are public and connects to the one it checked, so DNS rebinding can't reach inside. Never `httpx.get(url, follow_redirects=True)` on such a URL. The crawler has the same in `urls.pin`.
- **A project's `.labb/` is untrusted until agreed to** (`settings.needs_trust`, `untrusted`, `trust_all`; asked in `cli/app.py`'s `agree_to_project`). A new setting that runs code or skips asking goes in `needs_trust`. `permissions.save_allowed` trusts what labb writes. Tests get a temp `trust_file` from an autouse fixture in `conftest.py` (set by hand, not monkeypatch, so teardown order stays the tests' own).
- `permissions.check` asks every time for `RUNS_PROGRAMS` variables in front of a command and for git's reading commands where the repo's own config runs programs (`git_runs_programs`).
